01 / 我们想解决的问题

从能生成视频，
到能讲清楚一个产品。

一个面向独立开发者 / OPC 的产品视频导演：理解产品，讨论故事，再组织拍摄与制作。

探索分享 · 2026.09先做 30–60 秒 Web 产品介绍Skill → 工具服务 / MCP → Agent

这里按 OPC＝一人公司／独立开发者理解。

他们通常需要：

产品表达能力

功能很多，但不知道应该讲什么。

宣传片策划能力

不知道先讲痛点、效果，还是操作。

制作能力

不会设计动效、录制、配音和剪辑。

持续更新能力

产品改版后，旧视频很快过时。

所以可以这样定义：

给它产品仓库或网站，它先理解产品，提出值得讲的故事，与开发者确认后，自主准备素材、演示产品并制作宣传片；后续还能随着产品更新，生成新功能短片和不同渠道的版本。

核心交付不是一段视频，而是一套可修改、可复用的产品表达。

Repo / 网站→产品理解→故事协商→拍摄与制作→审片与修改

看完演示，再看当时的卡点

当时的三个卡点：故事、动效、Agent 执行能力。

回看年初这次尝试，“一卡一卡”的效果主要来自以下三个方面。

1. AI 讲故事的能力不够强

当时用到的大模型更像是在一个一个罗列功能，没能把功能串成有起承转合的故事。这首先是 AI 的故事组织能力问题，而不只是动画怎么排的问题。

2. Remotion 的动效使用不够丰富

年初这版能用上的 Remotion 动效和模板比较有限，反复使用同样的入场、切换效果，所以每一幕看起来都差不多。

3. 当时 AI Agent 的执行能力也不够强

当时这套 Agent 还做不到稳定、长时间地操作并录制产品，基本上只能截个图。缺少连续操作的视频素材，最后就容易变成一张张截图的展示。

故事串不起来、动效比较重复、素材主要是截图——三者叠加，形成了当时“一卡一卡”的效果。

从给截图加入场动画，转向提供界面参考帧和镜头要求，让模型生成视觉变化。先看当时做出的效果。

看完样片，再看这条路线的收益与问题

更快、更炫，但还不是完整的产品视频工作流。

1. 不读产品代码，先由人提供截图

当时使用的是图生视频入口，不是理解仓库的 Agent。要讲哪些功能、挑哪些界面、怎样准备首尾帧，都得先由人完成；模型接到的是画面与提示词，不是产品的完整逻辑。

2. 看着酷，表达仍围绕已有截图

马、红包和主题画面的运动很显眼，但相对“演示一个完整产品任务”，增量主要还是现有界面里的局部变化和视觉包装。它没有因此增加真实操作证据，也没有自动找出截图之外值得讲的新功能。

3. 单段短，调用和重试都要花钱

这支约 15 秒；要做更长的产品介绍，还得拆镜头、衔接和剪辑。生成较快是优势，但要把未采用的候选、重试和后期也计入成本，而不是只算最后留下的短片。

首尾帧用法、制作较快与费用感受来自这次历史制作经验；原片不能证明所有模型都必须输入首尾帧，也不能证明其时长上限。未提供当时的耗时和账单，因此不写具体速度或费用数字。

模型能帮我们做出短而炫的镜头；故事、产品事实与可控修改，仍需要另一层工作流。
04 / 第三次探索：让 Agent 直接录屏

这次有了操作过程，
但“录下来”仍不等于“讲清楚”。

让 Agent 操作产品、录制当前屏幕；录不到的部分，有时用网页补做，再放进视频。先看这次实际成片。

Biz Table / Agent 录屏成片 · 约 75 秒

用户提供的探索成果

原片，74.8 秒，1920 × 1080；点击加载后播放。

制作方式依据用户说明；本次检查成片，没有执行或复现片中的产品任务。仅凭 MP4 无法逐镜确认哪些是原始录屏、哪些是网页重建。

看完样片，再看第三次探索的卡点

比截图更接近任务，但证据、取景和剪辑仍需设计。

片中已经有“提出库存管理需求 → 推荐结构 → 空表 → 数据 → 看板 → 表单”的顺序，还有高亮和字幕，不是完全没有编排。问题在于它还保留了大量屏幕记录的表达方式。

1. 录的是整屏，观众却只需要看关键一步

约 33 秒的库存表、41–50 秒的看板里，左侧 Agent 对话、导航、表格和字幕同时出现。界面字小、信息密集，观众要自己寻找重点。需要裁切、局部放大和分阶段强调，而不是始终让整个工作台占满画面。

2. 录不到就用 AI 补做界面，真实与示意混在一起

按这次制作方式，录不到的部分会让 Agent 用网页补出来，成片里因此混入 AI 生成的界面。补标题和解释动画没有问题，但补做的产品界面或操作结果不能冒充真实录屏，需要明确标注并由开发者确认。

3. 跨镜头需要非常细致地对账

约 16.5 秒的推荐界面写“5 tables”，约 24.8 秒状态写“6 connected tables”。这至少需要解释或统一口径，不能只检查视频能否播放。界面中的表数、记录数、数据、字幕与宣称应逐项对应。

“录屏是真的”不代表整支片子的每个画面都经过事实验证。要把真实操作、解释性包装和重建示意分开管理。
05 / 三次实际尝试的优缺点

三种办法都能出片，
但各自只解决了一部分问题。

回顾当时的三次尝试
怎么做好在哪里有什么问题以后可以用来做什么
用 Remotion 把截图做成视频用的是真实截图，文字怎么写、画面怎么摆都能改。故事像在列功能，动效反复用，素材主要是截图，看起来一卡一卡。展示真实界面，给文字和图片加上可调整的动画。
把截图交给 AI 生成视频能比较快地让画面动起来，看着更炫。截图要自己准备；它不理解代码里的功能；一次生成的片段短，多试几次还要花钱。做开场或短特效镜头，但不能拿它证明产品真的完成了操作。
让 Agent 操作产品并录屏能看到产品怎么用，以及操作后的结果。录了整屏却看不清重点；录不到就补做界面；前后镜头的数据还得仔细核对。录下真实操作，剪掉等待、放大关键步骤，再用于成片。

看看 HyperFrames 是如何把这个整个能力工程化起来的。

06 / HyperFrames-剪辑工程化

给它一个产品网址，
一支视频是怎样做出来的？

沿着一次制作来认识 HyperFrames：我们提出要求，它组织素材与动画，我们审片修改，最后拿到成片。Skill、工具和编辑器都在这条过程中出现。

重点看它如何把制作过程工程化，再思考我们怎样组织讲解与真实操作，把产品讲得更清楚。

02 / 先固定需求

明确给谁看、讲什么、做多长，再创建工程

输入：网址、受众、核心卖点、时长、比例、是否配音，以及想协作确认还是自动推进。

执行：先由入口工作流确认 brief，初始化项目；同时检查声音等服务的可用状态，说明走本地还是托管服务。

留下：BRIEF.md 和 hyperframes.json。以后修改时读已有约定，不每次从零重新问一遍。

03 / 怎么取素材

不是只拿一张截图，而是形成有出处的素材清单

npx hyperframes capture "https://linear.app" -o ./capture --json

capture/
  screenshots/                 页面截图、可用时的完整长截图
  assets/                      捕获到的素材
  extracted/tokens.json        品牌颜色、字体等线索
  extracted/visible-text.txt   页面可见文字
  extracted/asset-descriptions.md  素材清单与描述

Agent 检查抓取是否成功，再根据清单给镜头选素材。滚动镜头可以移动长截图的视窗；局部放大需要足够清晰的区域截图。需要内部动作时，可保留截图底图、叠加捕获素材，或只重建运动组件。

重要规则：官方 Skill 已要求抓取失败就停下报告，不能为了继续出片自行造一个页面。只有用户明确改用提供的素材或同意风格化重建，才能换路径。原生素材缺失不等于获得虚构界面的授权。

补充素材：音乐、音效、图片等交给 media-use 工作流，Logo 从官方来源取；可选服务取决于账号与配置。

04 / 怎么把素材变成分镜

先决定每一幕要表达什么，再决定怎么动

先选择设计预设并映射品牌颜色、字体，形成 frame.md。再写 STORYBOARD.md；需要旁白时写 SCRIPT.md，每个镜头指向明确的候选素材。

镜头 02（示意）
目的：让观众看清一个任务从输入到结果的变化
素材：已核验的任务界面与结果画面
动作：先展示全局 → 聚焦关键区域 → 保留结果停顿
旁白：只讲已确认的产品能力
衔接：下一幕从当前结果继续，不重新开始
待确认：这是否是产品真实支持的任务？

协作模式先让用户审故事，按选择提供线框草图再确认布局；自动模式可减少中间提问。随后细化每幕布局、逐秒动作、素材与切换方式，不是直接跳到最终动画。

如果配音，先取得真实语音时长，再同步镜头长度；音乐、音效、字幕也和这份计划关联，而不是视频做完再随便贴一条声音。

05 / 怎么写动画

HTML 放元素，CSS 定外观，时间线安排动作

逐镜执行者读取该镜头的素材、布局、规则和品牌规范，写出 compositions/frames/NN-*.html；最后组装到 index.html。这里的 frame 是一幕画面，不是逐个视频帧都手写文件。

动画 Skill 提供动作规则、场景蓝图和转场规范，默认用 GSAP 组织时间线。例如，先让截图出现，再推进到重点，最后显示标注：

// 教学片段：省略完整 HyperFrames 页面与运行时注册
const tl = gsap.timeline({ paused: true });
tl.from(".product-screen", { opacity: 0, y: 24, duration: 0.5 }, 0);
tl.to(".product-screen", { scale: 1.12, duration: 0.8 }, 1.0);
tl.from(".callout", { opacity: 0, duration: 0.3 }, 1.8);

为什么暂停时间线？不是靠打开网页后“等动画播完”，而是让渲染器能定位到指定时刻，得到可重复的画面。官方规范要求可定位、确定性的动画，避免随机数或现实时间造成预览与导出不一致。

跨镜头延续的元素要约定切点上的位置、缩放、透明度和方向，避免两个子 Agent 各做各的、拼起来突然跳动。

06 / 我看预览，提出修改

这时打开 Studio：它就是当前工程的审片与编辑界面

组装各幕、声音和转场后，运行 lint 与 check；用 snapshot 检查每幕中间以及切点前后的画面，查看元素是否跳位、遮挡或不可读。

我们看到什么：中间是实际画面，下方是时间线，左侧查工程与素材，右侧调元素属性。不是另起一个产品，而是查看刚才制作出的同一个工程。

“第二幕看不清关键操作：
把结果区域放大一点，标注晚半秒出现。
保留旁白、品牌颜色和其他镜头。”

指得出的局部问题：可以在 Studio 调元素和时长，也可以让 Agent 定位第二幕 HTML，修改缩放或时间线。“其他镜头别变”同样是约束。

影响故事的变化：交给 Agent 更新分镜／脚本，再改受影响画面；旁白变长，还要同步镜头和字幕。两种编辑方式修改同一工程，不必把整支片子重新随机生成。

再检查一遍修改：看前后切点和完整播放。技术与画面检查通过，不等于功能事实已经验证；产品状态与数据仍要按证据核对。

07 / 我确认，工具导出

拿到的不只有 MP4，还有下一次能继续修改的工程

审片反馈处理完毕，按流程确认渲染；工具把确定的时间线导出为视频，同时保留需求、素材、分镜、源码、画面检查图和镜头编号。

打开工程预览：
npx hyperframes preview

检查修改后的工程：
npx hyperframes check

确认后导出：
npx hyperframes render --output video.mp4

本地工程命令示例，本次未执行。托管 MCP 路径则通过对话请求云端渲染，实际交付与工具能力以服务返回为准。

下一次修改继续使用这个工程：改文案、换素材、调节奏，而不是只剩一个无法拆开的最终视频。

查看实际产品片 Skill ↗查看动画 Skill ↗
从一个网址到可编辑成片：我们确认方向和结果，Agent 按 Skill 组织制作，工具执行，Studio 承接审片修改。

值得借鉴的是工程化，但工程化不等于效果已经足够好。

路由 → 产品片 Skill → 取素材、提方向并确认 → 写动画 → 检查和修改。它把原来分散的工作变成了有规范、有中间产物、可继续编辑的流程。

但从这支 Linear 样片看，仍有“标题与界面逐幕出现”的动态 PPT 感：换页更流畅、动作更丰富，不等于产品价值已经通过连续镜头讲清楚。

所以我们借鉴它的工作流、动画规范和编辑机制，不直接照搬样片的表现方式；也不能据此认定它的技术上限只到这里。

07 / 我们的方案

串场讲清楚，产品展示看得明白，
最后交付一个可复用的工程。

先改善当前“可动 PPT”的表达：串场负责解释和连接，产品展示负责真实操作与结果。不是先承诺微软级，而是先把这两部分做得连贯、清楚、可修改。

以下是拟验证的制作方案，不是已经实现的全自动能力。优先复用 HyperFrames 的流程、规范、编辑与渲染，不把当前样片的表现方式当成最终答案。

理解产品、确认故事→镜头任务单→串场 / 产品展示→编排与对账→可复用工程
01 / 理解产品，先确认故事

先决定讲什么，再决定怎么做画面

读取授权代码、文档和运行页面，与开发者确认目标用户、核心价值、已经实现的功能，以及用哪个真实任务来证明。

落档：已确认的故事线、产品事实与证据、关键文案和不应改变的要求。后面的 Agent 共用这份依据，不各自重新理解一遍。

02 / 将故事拆成镜头任务单

每幕不仅有台词，还要有目的、焦点和前后状态

任务单字段要说清楚什么
镜头编号与表达目的这一幕让观众理解什么；对应哪个已确认卖点。
类型与制作方式真实操作录屏，还是 HTML 讲解；是否需要另行确认生成素材。
焦点与起止状态观众看哪里，镜头开始和结束时画面是什么。
素材与证据来源用哪段录制、哪个界面或设计素材；操作结果如何核实。
镜头衔接与声音怎样接上一幕、下一幕；旁白、停顿与关键动作怎样对应。

这是两条制作线共同遵守的约定。只把故事拆成几段文字，再各做各的，很可能又拼成一组动态 PPT。

03 / 串场与产品展示，分别制作但保持连贯

串场 / 解释问题，连接前后镜头

默认 HTML，用户看过不满意再接 AI 生视频

让同一组元素归类、连接、变化，把上一幕的结果带入下一幕的操作。串场要解释“为什么”和“接下来做什么”，而不只是标题飞入、换页。

先给出 HTML 版本让用户看效果；用户确认效果不好后，再提出 AI 生视频方案，确认素材权限、预算和用途后执行，不由 Agent 自行跳过这一步。

交付：保留 HTML 源码或 AI 原始输出、时长与声音约定，并明确标记“HTML 制作”或“AI 生成”。生成画面不能冒充实际产品操作。

产品展示 / 关键操作与真实结果

默认录制，Agent 自己规划剪辑和重点强调

用授权测试账号和数据实际操作、核对结果。Agent 根据要突出的内容规划加速、减速、剪切、裁切和放大，并保留原始录像及时间对应关系。

录制或剪辑仍无法表达重点时，可以用 HTML 补充高亮、局部动画或重建示意。明确说明哪些是实际录制、哪些是 HTML 写的；未执行过的操作不能被说成已经真实完成。

交付：原始录像、剪辑计划、关键时间点、HTML 源码与素材清单。混合镜头同时标记“录屏 + HTML 叠加”，重建界面标记“HTML 示意”。

04 / 在统一工作台编排、对账和修改

先验单镜头，再验整片；画面、字幕和声音一起对账

单镜头交付时检查任务单和素材，组装后再检查跨镜头关系。可复用 HyperFrames 的时间线、预览、编辑与渲染能力，增加面向产品的对账和反馈界面。

来源标注：在审片工作台和交付清单中逐镜标明“实际录屏 / HTML 制作 / AI 生成”；混合镜头逐层记录。HTML 重建或生成画面可能被误认成真实操作时，成片中也明确标为示意。

事实对账

功能、字段、数字、状态和字幕是否一致？操作结果能否追溯？哪些是录屏、哪些是解释或重建示意？不确定项交给开发者确认。

观看效果对账

关键一步能否看清？讲解是否接上操作？镜头是否突然跳转？声音与画面是否同步？观众是否能跟上同一条主线？

字幕对账

字幕是否对应最终配音和画面？产品名、数字有没有写错？加减速或剪切后，出现和消失的时间是否仍准确？字号、断句和位置是否清楚、不挡关键操作？

配音对账

是否使用确认后的文案？产品名和术语读音是否正确？语速、停顿是否跟得上操作？跨镜头音量和音色是否一致，有没有截断句子或漏读？

音效与音乐对账

点击、提示和转场音效是否落在对应动作上？有没有重复、错位或突然截断？音乐和音效是否盖住配音？混音有无爆音，开头结尾是否自然，素材授权是否明确？

修改闭环：问题附时间点、镜头编号和字幕／音轨 → 退回对应制作环节修改 → 联动复查画面、配音、字幕和音效 → 再审片。改时长或剪切后必须重新校准同步关系；不是整支重新生成，也不是自动检查通过就免去人的判断。

我们重点补的能力，落实为三个环节

镜头设计与分工 Skill

把产品证据和故事变成可执行任务单，判断讲解与录屏各承担什么，而不只是再加动效。

连续性编排 Skill

让两条制作线共享焦点、起止状态和声音约定，在组装时沿同一问题、元素或结果自然衔接。

审片与修订工作台

在现有技术检查上，增加产品对账、观看反馈和定向返工；用工具执行重拍和编辑，用版本记录管理变化。

05 / 最后留下可复用工程，不只是一个 MP4

保留故事与镜头任务单、原始录屏、串场 HTML／生成素材、配音字幕、统一时间线和审片记录，并关联到素材来源及产品版本。

产品改了，能定位需要重拍或修改的片段；换渠道，可以调整尺寸、字幕和节奏。统一管理授权、预算和版本，重新检查受影响镜头，不让各模块各改各的。复用开源能力保留来源并遵守许可。

怎么证明这样分工确实更好？

用同一个产品、已确认的故事和相同总预算，对比直接使用 HyperFrames 的结果与这条混合流程。分别记录素材准备、人工审片、调用费用和返工次数。

看观众能否理解同一个核心价值、关键步骤是否更清楚、事实问题是否更少、修改是否更集中。不能只比动效数量，也不能靠更多人工和无限重试宣称胜出。

近期先做到：串场不是翻页，产品展示不只是整屏记录，交付后还能复用和修改。接下来再看微软级的进阶差距。
